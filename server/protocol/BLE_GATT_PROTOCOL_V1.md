# ClearMeeting Recorder BLE GATT Protocol V1.0

Status: Draft frozen for Windows-client and nRF52840 implementation
Transport: Bluetooth LE GATT
Byte order: little-endian for every multi-byte integer
Text encoding: UTF-8

## 1. Design goals

- The recorder always records locally; BLE is a real-time transport, not the only copy.
- Audio loss must not block later audio frames.
- The Windows client can discover missing frames and pull logical chunks from MicroSD.
- The Windows client can send ASR captions back to the recorder for e-paper display.
- Control operations that change state are acknowledged at application level.
- V1 packets remain decodable when optional fields are added in a later version.

## 2. BLE link requirements

| Item | V1 requirement |
|---|---|
| GAP device name | `ClearMeeting-XXXX` where `XXXX` is the final 4 hex digits of the device ID |
| Preferred ATT MTU | 247 bytes; protocol must still work with a smaller negotiated MTU |
| Preferred PHY | LE 2M; fall back to LE 1M |
| Preferred connection interval | 15-30 ms while recording; 100-200 ms while idle |
| Pairing | LE Secure Connections and bonding |
| Production authorization | Six-digit passkey shown on e-paper; confirm with REC button |
| Development mode | Just Works may be enabled only by a compile-time development option |

The application must calculate packet fragmentation from the negotiated ATT payload size:

`att_value_max = negotiated_mtu - 3`

The recorder must never assume that the MTU negotiation succeeded.

### 3.2 ClearMeeting Recorder Service

Base namespace: `9f4cxxxx-7d2a-4a6b-b8a1-5c2e7f310001`

| Name | UUID | Direction | Properties | Purpose |
|---|---|---|---|---|
| Recorder Service | `9f4c0001-7d2a-4a6b-b8a1-5c2e7f310001` | - | Primary service | Custom service |
| Command | `9f4c0002-7d2a-4a6b-b8a1-5c2e7f310001` | Windows -> recorder | Write, Write Without Response | Commands and request packets |
| Event | `9f4c0003-7d2a-4a6b-b8a1-5c2e7f310001` | Recorder -> Windows | Indicate | Command results and important state changes |
| Live Audio | `9f4c0004-7d2a-4a6b-b8a1-5c2e7f310001` | Recorder -> Windows | Notify | Real-time audio frames |
| Bulk Data | `9f4c0005-7d2a-4a6b-b8a1-5c2e7f310001` | Recorder -> Windows | Notify | MicroSD chunk recovery and session metadata |
| Caption | `9f4c0006-7d2a-4a6b-b8a1-5c2e7f310001` | Windows -> recorder | Write Without Response, Write | Partial/final ASR text for the e-paper |
| Status | `9f4c0007-7d2a-4a6b-b8a1-5c2e7f310001` | Recorder -> Windows | Read, Notify | Periodic device state and counters |

Critical state transitions use Event indications. Audio and bulk data use notifications so a lost packet cannot stall the stream.

## 4. Identifiers and counters

### 4.1 Device ID

`device_id` is a stable 64-bit value derived once at manufacturing time and stored in protected flash. It must not be a Bluetooth MAC address.

### 4.2 Session ID

`session_id` is an unsigned 64-bit random value generated by the Windows client. A recorder-button-only session may be generated by the recorder. Zero means no active session.

### 4.3 Frame and chunk numbering

- `frame_seq` starts at zero for each session and increases for every 20 ms audio frame.
- Sequence arithmetic does not wrap during a normal meeting; a session must be closed before `0xFFFFFFFF`.
- One logical recovery chunk contains 50 frames, representing one second.
- `chunk_index = frame_seq / 50`.
- Chunks are the synchronization unit; the physical MicroSD file may use longer segments.

## 5. Live Audio packet

Live Audio characteristic value:

| Offset | Size | Field | Description |
|---:|---:|---|---|
| 0 | 1 | version | `0x01` |
| 1 | 1 | packet_type | `0x10` live audio |
| 2 | 1 | flags | See below |
| 3 | 1 | codec | `0x01` IMA-ADPCM, `0x02` PCM16LE |
| 4 | 8 | session_id | Meeting session |
| 12 | 4 | frame_seq | 20 ms frame number |
| 16 | 4 | timestamp_ms | Milliseconds since session start |
| 20 | 2 | sample_count | Normally 320 |
| 22 | 2 | payload_len | Codec payload length |
| 24 | N | payload | Encoded audio |
| 24+N | 2 | crc16 | CRC-16/CCITT-FALSE over offsets `0..23+N` |

Flags:

| Bit | Meaning |
|---:|---|
| 0 | First frame of session |
| 1 | Last frame of session |
| 2 | Audio discontinuity occurred before this frame |
| 3 | Frame has also been committed to MicroSD |
| 4-7 | Reserved, transmit as zero |

### 5.1 V1 audio profile

- Sampling: 16 kHz
- Resolution before encoding: signed 16-bit
- Channels: mono
- Frame duration: 20 ms
- Samples per frame: 320
- Codec: IMA-ADPCM, 4 bits/sample
- ADPCM payload: 164 bytes
  - bytes 0-1: signed 16-bit initial predictor
  - byte 2: initial step index, range 0-88
  - byte 3: reserved, zero
  - bytes 4-163: 320 ADPCM nibbles

Each frame is independently decodable. Encoder state must reset from the predictor and step index stored in that frame; losing one notification therefore does not corrupt later frames.

With the 26-byte protocol overhead, a normal packet is 190 bytes and fits inside an ATT MTU of 247.

If the negotiated ATT value is smaller than the packet, the recorder uses the generic fragmentation envelope in section 9. Live streaming should normally be refused below MTU 200 and the client should fall back to chunk synchronization.

## 6. Command packet

Command characteristic value:

| Offset | Size | Field |
|---:|---:|---|
| 0 | 1 | version = `0x01` |
| 1 | 1 | opcode |
| 2 | 1 | flags |
| 3 | 1 | reserved = `0` |
| 4 | 2 | request_id |
| 6 | 2 | payload_len |
| 8 | N | payload |
| 8+N | 2 | crc16 |

Commands that modify state use GATT Write and must receive an Event response with the same `request_id`. Idempotent high-frequency commands may use Write Without Response.

| Opcode | Name | Payload |
|---:|---|---|
| `0x01` | HELLO | `client_protocol_min:u8, client_protocol_max:u8, client_caps:u32` |
| `0x02` | GET_STATUS | Empty |
| `0x10` | START_SESSION | `session_id:u64, unix_time_ms:u64, codec:u8, sample_rate:u32, channels:u8` |
| `0x11` | STOP_SESSION | `session_id:u64, reason:u8` |
| `0x12` | INSERT_MARK | `session_id:u64, timestamp_ms:u32, mark_type:u8` |
| `0x20` | LIST_SESSIONS | `before_unix_ms:u64, limit:u16` |
| `0x21` | GET_CHUNK_MAP | `session_id:u64, first_chunk:u32, chunk_count:u16` |
| `0x22` | READ_CHUNKS | `session_id:u64, first_chunk:u32, chunk_count:u16` |
| `0x23` | CANCEL_BULK | `transfer_id:u16` |
| `0x30` | SET_TIME | `unix_time_ms:u64, timezone_minutes:i16` |
| `0x31` | SET_DISPLAY_MODE | `mode:u8, refresh_period_ms:u16` |
| `0x40` | DELETE_SESSION | `session_id:u64, confirmation:u32` |

`DELETE_SESSION.confirmation` must equal the low 32 bits of `session_id XOR 0xC1EA4D1E`; this prevents accidental deletion caused by malformed packets. Deletion is still rejected while recording.

## 9. Generic fragmentation envelope

Bulk Data always uses this envelope. Live Audio uses it only when unavoidable.

| Offset | Size | Field |
|---:|---:|---|
| 0 | 1 | version = `0x01` |
| 1 | 1 | packet_type: `0x40` bulk fragment, `0x41` fragmented audio |
| 2 | 2 | transfer_id |
| 4 | 2 | fragment_index |
| 6 | 2 | fragment_count |
| 8 | 2 | fragment_len |
| 10 | N | fragment_data |
| 10+N | 2 | crc16 |

Fragments belonging to one item have the same `transfer_id`. `fragment_count` is fixed for that item. A receiver discards an incomplete item after 10 seconds; recovered data can be requested again at chunk level.

## 10. Bulk recovery format

Each recovered logical chunk is serialized before fragmentation:

| Offset | Size | Field |
|---:|---:|---|
| 0 | 1 | version = `0x01` |
| 1 | 1 | item_type = `0x01` audio chunk |
| 2 | 8 | session_id |
| 10 | 4 | chunk_index |
| 14 | 4 | first_frame_seq |
| 18 | 2 | frame_count, normally 50 |
| 20 | 4 | encoded_len |
| 24 | N | Concatenated length-prefixed audio payloads |
| 24+N | 4 | crc32 IEEE over offsets `0..23+N` |

The chunk map returned by `GET_CHUNK_MAP` is a bitmap: bit 0 represents `first_chunk`; one means the complete chunk exists on MicroSD.

The Windows client compares received live `frame_seq` values with the chunk map after recording. Missing ranges are pulled with `READ_CHUNKS`, deduplicated by `(session_id, frame_seq)`, then uploaded to the cloud as recovered audio.

## 11. Caption packet

Caption characteristic value:

| Offset | Size | Field |
|---:|---:|---|
| 0 | 1 | version = `0x01` |
| 1 | 1 | caption_type: 0 partial, 1 final, 2 clear, 3 system message |
| 2 | 1 | flags |
| 3 | 1 | reserved = `0` |
| 4 | 8 | session_id |
| 12 | 4 | revision |
| 16 | 2 | fragment_index |
| 18 | 2 | fragment_count |
| 20 | 2 | text_len |
| 22 | N | UTF-8 text fragment |
| 22+N | 2 | crc16 |

Flags: bit 0 high priority, bit 1 replace current line, bit 2 append to history, bit 3 meeting-summary notification.

Rules:

- Revisions increase monotonically per session.
- The recorder ignores a partial caption with a revision lower than the last displayed revision.
- Partial text replaces the current line; final text is committed to the local caption history.
- The Windows client coalesces ASR updates and normally sends at most one display revision per second.
- All fragments of a revision must arrive before it is displayed. The incomplete revision expires after three seconds.
- Write Without Response is used for fragments; every tenth revision and every final caption uses GATT Write so the client can detect a broken link.

## 12. CRC definitions

### CRC-16/CCITT-FALSE

- Polynomial: `0x1021`
- Initial value: `0xFFFF`
- Reflect input/output: false
- Final XOR: `0x0000`
- Check value for ASCII `123456789`: `0x29B1`

### CRC-32 IEEE

- Polynomial: `0x04C11DB7` reflected form `0xEDB88320`
- Initial value: `0xFFFFFFFF`
- Reflect input/output: true
- Final XOR: `0xFFFFFFFF`
- Check value for ASCII `123456789`: `0xCBF43926`

## 13. Required connection sequence

1. Windows scans by service UUID and connects.
2. Pair/bond when needed.
3. Negotiate MTU, data length, PHY and connection parameters.
4. Enable indications on Event.
5. Enable notifications on Status, Live Audio and Bulk Data.
6. Send HELLO and verify the negotiated protocol version.
7. Read Status and reconcile any active recorder session.
8. Start or resume live audio.
9. During recording, monitor `frame_seq`; record gaps without blocking playback/upload.
10. Send coalesced ASR captions through Caption.
11. After STOP_SESSION, request the chunk map and recover missing chunks.
12. Persist session completion only after live and recovery data have been reconciled.

## 15. V1 implementation boundaries

- BLE does not carry DeepSeek prompts or cloud credentials.
- The recorder never needs to understand WebSocket or cloud protocol details.
- The Windows client owns BLE-to-cloud session mapping and deduplication.
- The cloud remains authoritative for final transcript, summary, decisions and action items.
- Firmware V1 may omit session deletion from the UI, but must reserve the opcode and reject it cleanly if unsupported.

## 16. Acceptance tests

- Sustain 60 minutes of audio with no unbounded RAM growth.
- Disable Bluetooth for 30 seconds, reconnect, recover missing chunks and produce a gap-free frame sequence.
- Lose a single Live Audio notification; the next ADPCM frame must decode independently.
- Negotiate MTU 247 and verify normal audio packets are not fragmented.
- Reconnect while the recorder continues recording; HELLO + Status must expose the active session.
- Send partial captions faster than 1 Hz; the recorder must display only coalesced revisions.
- Send UTF-8 Chinese text split through a multi-byte character; reassembly must occur before UTF-8 decoding.
- Corrupt CRC and verify the packet is rejected without changing state.
- Power-cycle the Windows client and recover from its persistent session/frame database.
