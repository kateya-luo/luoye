# ClearMeeting 平台架构与路线图

> 开发导向文档：不是愿景 PPT，是开发北极星。每个里程碑给出**交付物 + 验收标准 + 接口粒度**。

## 0. 一句话定位

一个"**采集 → 理解 → 议程**"的个人智能平台，以 **WiFi 录音笔**为统一入口，
用**同一套后端**支撑两条业务线（工作 / 学生），两条线是同一平台的两张皮肤，不是两个系统。

## 1. 全景架构

```
                        ┌──────────────── 设备端（录音笔 ESP32-S3）────────────────┐
                        │  双数字硅麦 → I2S/PDM → 16k PCM → SD卡（先录后传，真相源）  │
                        │  3键 REC/MARK/BACK · 3灯 · 2.11"墨水屏(0.6s快刷) · RTC · 电量计 │
                        └───────┬──────────────────────────────────▲────────────────┘
                    音频上行(通道B HTTP分片)                文字/事件下行(新，WS/SSE)
                                │                                    │
        ┌───────────────────────▼────────────────────────────────────┴──────────────────┐
        │                              服务器（FastAPI）                                   │
        │  ┌── 支柱A：采集理解流水线（已有）──────────┐  ┌── 支柱B：日历/议程（新建）──────┐ │
        │  │ 通道A实时WS → funasr 流式ASR → 字幕      │  │ events / todos / reminders     │ │
        │  │ 通道B可靠上传 → .b.pcm → 断网补洞         │  │ recurring(课程表) / 提醒调度    │ │
        │  │ speaker(CAM++)说话人 · 翻译步(新) · 纪要 │  │ 语音待办抽取 → 入库             │ │
        │  │ DeepSeek 纪要/翻译 · SQLite 持久化       │  │ RTC 唤醒提醒                    │ │
        │  └──────────────────────────────────────────┘  └────────────────────────────────┘ │
        │        设备层（新）：配对/令牌/吊销 · 状态上报 · OTA固件分发 · HTTPS                  │
        └──────────────────────────────────────────────────────────────────────────────────┘
                                │                                    │
                    ┌───────────▼──────────┐            ┌────────────▼─────────────┐
                    │ 手机App：配网/配对/    │            │ Web/桌面：会后工作台      │
                    │ 观战字幕/设备管理      │            │ 历史/回放/编辑/导出        │
                    └──────────────────────┘            └──────────────────────────┘
```

**核心不变量**：重 AI 全在云端；设备只负责"可靠采集 + 常驻显示 + 按键捕获"。

## 2. 两根后端支柱

### 支柱 A：采集 → 理解流水线（已有，直接复用）
现状已上线：双通道（实时WS + 可靠HTTP上传）、断网补洞、说话人分离、DeepSeek 纪要、SQLite。
**会议纪要 = 听课笔记**（同一条链，换措辞）。本支柱**新增**一步：**翻译**（见 §5.1）。

### 支柱 B：日历 / 议程 / 提醒（全新，最大的新地基）
当前服务器只有 meetings/summaries，**没有** events/todos/reminders/recurring。
语音待办、课程表、"晚7点提醒"全落在这。**建议独立成一个服务**（`agenda`），不塞进现有 server。

数据模型（最小集）：
```
event      (id, owner, type[meeting|class|todo|reminder], title, start, end,
            recurrence_rule, source[voice|manual|meeting], linked_meeting_id, created_at)
reminder   (id, event_id, remind_at, channel[screen|led], fired_at)
todo       (id, owner, text, due, done, source_event_id)
```
课程表 = 一组 recurring event；语音待办 = 一条 voice-source event/todo；提醒 = event 派生的 reminder。

## 3. 设备端（录音笔）

### 硬件（已定板，见 board.pdf / mic.pdf）
> 三键语义、屏幕页面、离线行为、LED 等**交互定稿**见 [RECORDER_CARD_SPEC.md](RECORDER_CARD_SPEC.md)。
ESP32-S3 · 2× Infineon IM72D128(PDM, 69dB SNR) · microSD(SPI) · 2.11"墨水屏(0.6s快刷) ·
PCF8563 RTC · MAX17048 电量计 · BQ25186充电+TPS63001 · 3键(REC/MARK/BACK) · 3灯(REC/FULL/CHG)

### 固件职责（笨设备原则）
- **采集**：I2S PDM RX → 双麦降混 16k 单声道喂上传；原始双声道可选存 SD（留降噪后路）
- **存储**：先写 SD（PCM + RTC时间戳 + session元数据），上传游标做断点续传
- **上行**：复用通道B（小包连传，断网合批）→ `final=1` 收尾触发定稿
- **下行**：接收译文/状态/议程/待办确认，渲染到屏（新）
- **屏三态**（见 §3.1）· **RTC 定时唤醒提醒** · **LED 状态机** · **OTA** · **低电先写完 SD 再关机**

### 3.1 墨水屏三态
| 态 | 显示 | 刷新 | 前提 |
|---|---|---|---|
| **待机** | 时钟 + 今日议程 + 下一个提醒 | 分钟级/事件触发 | 离线也有 |
| **录制中** | 顶栏状态(录音/时长/电量/积压) + 屏底**逐句译文/确认句** | 每句刷(3~10s) | 需在线+下行 |
| **捕获** | 待办确认"已记：19:00 学生会开会" | 单次 | 需在线 |

> 提醒当前仅视觉（LED+屏）。**硬件缺声/振**——若提醒是学生线关键卖点，下一版加蜂鸣器/马达（改板决策）。

## 4. 落叶通信契约（v0.12.0 已收敛）

正式边界只有 `/api/v1`，详细字段、幂等规则和错误码见 [LUOYE_DEVICE_API_V1.md](LUOYE_DEVICE_API_V1.md)。

- 配对：`/api/v1/device/pair/*` 与 `/api/v1/me/devices/claim`。
- 录音：`/api/v1/device/sessions/*`，PCM S16LE/16 kHz/单声道，分片 SHA-256 与幂等键。
- 字幕/翻译/状态：设备按 revision 读会话 state，网页与设备使用同一会话数据。
- 议程：`/api/v1/device/agenda?after_revision=`。
- 语音待办：`/api/v1/device/todos/*`。
- 兼容性：`/api/v1/build-info`。

旧全局配对码和设备 WebSocket 方案已于 v0.12.0 一次性移除，不再作为备用协议。

## 5. 新增能力清单

### 5.1 实时翻译管道（v2 设计，2026-07-08 定稿）

**两个目标场景（同一管道，参数不同）**：
| | ① 中英混合会议（工作线） | ② 学生听英文课（学生线） |
|---|---|---|
| 输入 | 中英夹杂、有对话停顿（VAD 终句够密） | 连续英文讲课、终句稀疏（实测 40s 不出终句） |
| 方向 | 双向：非目标语言句→目标语言，**同语言跳过** | 固定 EN→ZH |
| 形态 | 逐句对照（字幕行下挂译文） | 译文为主连续流（卡屏 15s 节拍） |
| 断句 | VAD 终句 | **强制断句**（见下） |
| 会后 | 双语会议记录 | 双语课堂笔记 |

**管道结构（每会话一个实例，通道A/设备路径共用）**：
```
ASR 终句流 → 同语言检测(字符集启发式，同语跳过不调API)
          → 串行翻译队列(保序、并发=1，杜绝乱序/堆积)
          → 带滚动上下文调用(携带前3对原文+译文，保术语/代词一致)
          → 下推 translation(带seg_id) + 落库 segments.translation
          → 服务端逐句记录 translate_latency_ms(拿数据不拿体感)
```

**连续讲课的断句（场景②的命门）**：优先尝试给 FunASR 传 VAD 最大段长参数
（压到 ~10s，强制断句 → 终句变密，问题消失）；协议不支持再退而在服务端做
伪句切分器（partial 累积超 7s/20字 按标点切段翻译，翻后不回改，保持流畅）。

**明确不做**：逐 partial 重翻回改（成本翻倍+界面闪变）；本地 MT 模型（触发条件见决策记录：延迟>4s常态/量大限流/隐私要求/断外网刚需，届时 DEEPSEEK_BASE_URL 指向本地 OpenAI 兼容服务零代码切换）。

### 5.2 设备层
配对/令牌/吊销 · 状态上报 · OTA 分发 · **HTTPS 必须**（笔走公网传音频+令牌不能明文，启 nginx 443）。

## 6. 两条业务线 = 同一平台的皮肤

| 能力 | 工作线 | 学生线 | 底层实现 |
|---|---|---|---|
| 长录音理解 | 会议纪要 | 听课笔记 | 支柱A（同一条）|
| 实时文字 | 实时翻译 | 实时听译 | ASR→翻译→下行（同一条）|
| 结构化捕获 | 语音待办 | 课程表+待办 | 支柱B 日历（同一个）|
| 提醒 | 会议提醒 | "19:00 学生会" | reminder + RTC 唤醒 |

**纪律：底座只建一次，业务线只是默认配置 + UI 皮肤。**

## 7. 分期路线图

| 里程碑 | 交付物 | 验收标准 |
|---|---|---|
| **M0 现状** | 会议纪要平台（浏览器/桌面/Android）、双通道、补洞、SQLite | 已上线 ✅ |
| **M1 在线伴侣底座** | 设备配对+令牌；音频上行(复用)；**文字下行WS**；固件：录音→SD→上传+屏三态骨架+LED；**假录音笔脚本** | 一支笔(或假笔)录一场会 → 服务器出纪要；笔屏显状态+最近确认句 |
| **M2 实时翻译** | ASR→翻译步；下行推译文；固件录制态显译文 | 外语音频 → 笔屏逐句显中文译文，延迟可接受 |
| **M3 日历支柱** | `agenda` 服务(event/todo/reminder/recurring)；MARK语音待办；课程表；RTC提醒 | 说"晚7点开会"→日历有条目→到点笔提醒 |
| **M4 设备运营化** | 状态上报；OTA；**HTTPS 上线**；App 设备管理页 | 远程升级一支笔成功；App 看到电量/存储/固件 |
| **M5 业务分皮** | 工作线/学生线 各自 UI 皮肤与默认配置 | 两条线各自体验完整 |

### M3 当前落地（2026-07-12）

- ✅ SQLite 四表：`agenda_events` / `agenda_reminders` / `agenda_todos` / `agenda_voice_captures`；
- ✅ `POST /api/agenda/events`、`GET /api/agenda/today`、`POST /api/agenda/voice-todo`，另有待办勾选接口；
- ✅ 中文/英文口语时间、跨天/时区、daily/weekly/BYDAY 展开测试；有 DeepSeek 时走 LLM 抽取，无 key 时确定性解析兜底；
- ✅ 网页“议程待办”页、30 秒刷新和浏览器通知；`fake_pen.py --voice-todo` 可模拟 MARK；
- ✅ 设备音频分片响应携带 `latest_text` / `latest_translation`，粗屏无需额外轮询；
- ⏳ 真板 MARK 独立 PCM 截取、设备 RTC 下行提醒、课程表批量导入仍属后续阶段。

## 8. 现在就动的第一步（M1 开工点）

**不是先写固件，是先定死《设备接入契约》并用"假录音笔"跑通链路**：
1. 冻结 §4 的接口（配对 / 音频上行 / 文字下行 WS）。
2. 写一个 Python **假录音笔脚本**：读一个 wav → 按通道B分片上传 → 开 device WS 收字幕/译文打印到终端。
3. 服务端补最小设备层（配对+令牌+device WS 推送），复用现有 ASR/纪要。
4. 这样硬件还在打样，M1 链路已在服务器上验证完毕；笔回来刷固件即通。

固件按 §3 职责实现；屏先做"待机+录制"两态，捕获态随 M3。
